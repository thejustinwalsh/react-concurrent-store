---
title: Reading a store urgently
description: Opting one reader out of a transition the rest of the tree is waiting on.
---

`useStore` honours what the caller said. A dispatch made inside
`startTransition` reaches its readers as a transition, and they move with the
rest of the tree.

Sometimes one reader cannot wait — a like count, a toggle, an input. That
reader can opt out:

```tsx
import { useStoreUrgent } from "react-concurrent-store/urgent";

function LikeCount() {
  const likes = useStoreUrgent(store, (state) => state.likes);
  return <span>{likes}</span>;
}
```

It updates at the caller's priority rather than waiting for a pending
transition, and it never shows a fallback: the value it reads is already
computed and its handle already resolved, so there is nothing to suspend on.

## What it reads

Not `getState()`. That is the chronological state — every action in dispatch
order — so while a navigation is pending it holds a page that has not loaded.
A reader given that suspends on data that is not there.

It reads the state the tree may show right now: the urgent actions applied to
what is on screen, without the pending transition. That is the fold described
in [Rebasing](/react-concurrent-store/explanation/rebasing/), and it is why
this hook exists on this store and not on a plain one.

| | `useStore` | `useStoreUrgent` |
| --- | --- | --- |
| a navigation dispatched in a transition | waits for it | ignores it |
| a like dispatched urgently | shows it | shows it |
| mounting while a navigation is pending | what its siblings show | the urgent fold |
| can show a Suspense fallback | yes, if the state it reads is unsettled | no |

## Pick one hook per slice

Two readers of the same slice, one through each hook, will disagree while a
transition is outstanding. That is what asking for different semantics means,
not a bug — but it is a disagreement your users can see, so choose per slice
and stay with it.
