---
title: Selectors and re-renders
description: Why useStore has no equality argument, and what to use instead.
---

A selector narrows a store to the part a component actually needs. The
component re-renders when that part changes — and "changes" means the selector
returned a different reference.

```tsx
const name = useStore(store, (state) => state.user.name);
```

That works for strings, numbers and anything else already stable in your state.
It stops working the moment a selector builds something:

```tsx
// A new object every call, so this re-renders on every action.
const user = useStore(store, (state) => ({
  name: state.user.name,
  email: state.user.email,
}));
```

## The previous result

A selector receives two arguments: the current state, and **its own previous
result**. Returning that previous value unchanged is how you say nothing
happened.

```tsx
const visible = useStore(store, (state, previous) => {
  const next = state.todos.filter((todo) => !todo.done);
  const same =
    previous?.length === next.length &&
    previous.every((todo, i) => todo === next[i]);
  return same ? previous : next;
});
```

This is the whole mechanism. There is no separate equality channel — identity
is the signal, and you decide when to preserve it.

## Why there is no equality argument

React ships `useSyncExternalStore` without one and leaves
`useSyncExternalStoreWithSelector` to a separate module. `useStore` follows
that, for the same reason: comparison is a policy question. Shallow, deep,
structural sharing and "recycle unchanged subtrees" are all valid, they have
very different costs, and a hook that picks one for you makes the other three
awkward.

Giving the selector its previous result covers every one of them without the
hook needing to know which you chose.

## When you just want shallow

Writing that comparison by hand each time is tedious, so the wrapper exists:

```tsx
import { useStoreWithEqualityFn } from "react-concurrent-store/with-equality-fn";
import { shallowEqual } from "react-redux";

const user = useStoreWithEqualityFn(
  store,
  (state) => ({ name: state.user.name, email: state.user.email }),
  shallowEqual,
);
```

It ships from its own entry point, so it adds nothing to your bundle unless you
import it. Any comparison function works.

## When a selector throws

A selector is called in two quite different situations, and a throw means
something different in each.

**During render**, the selector is producing the value the component is about
to show. A throw there is a real error and is left alone — it reaches your
error boundary, exactly as it would from any other code in the component body.

**Speculatively**, the store calls the selector to decide whether a reader needs
to re-render at all: when an update is published, when a view first attaches,
and when the tree commits past it. A throw there is not necessarily an error.
It is usually the zombie-child case — the selector is being asked about a state
its component is not going to be rendered with, because a parent has already
removed it. So the store swallows it and forwards the update, letting the
render decide. If the component really is about to render with that state, the
selector throws again during render and the boundary catches it.

```tsx
// If `id` has just been deleted from the store, this throws while the store is
// only asking whether this reader is affected. That is not an error. It throws
// again during render only if this component is still mounted and reading it,
// and then it reaches the boundary.
const item = useStore(store, (state) => {
  const found = state.items[id];
  if (found === undefined) throw new Error(`missing ${id}`);
  return found;
});
```

The rule, in one line: **a speculative throw is a question the store cannot
answer, so it asks render instead; a throw in render is an error.** This is the
behaviour React-Redux's `useSelector` suite specifies, and it is checked here
against both a direct test and a React-Redux-shaped harness.

## Selectors run during render

The selector is called while your component renders, so the props it closes
over and the state it reads always come from the same moment. A selector that
throws because its props are briefly out of date does not break the dispatch
that caused it — the component simply renders again with matching props.

This is the "zombie child" case, and it is why the selector is not evaluated
eagerly when the store changes.
